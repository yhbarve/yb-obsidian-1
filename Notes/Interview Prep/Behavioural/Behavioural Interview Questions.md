**Q1. Tell me about a time when you had a fundamentally different technical viewpoint from a peer or teammate. How did you handle the disagreement to reach a successful consensus?**
- As the backing lead for Fit4Me one of the tasks my team had to do was to build the APIs for user registration and profile creation. This involved endpoints like sign up and login.
- I had a minor technical disagreement with a team mate of mine about the handling of critical inputs like usernames, passwords, and date of birth. We needed to implement a validation system to ensure that all incoming data was clean and correctly formatted. For example we needed to ensure that a user's date of birth wasn't accidentally set in the future or that an email address had the correct format.
- My team mate, who was also working with me, argued that all these checks and validation on the front end was enough. The reasoning behind this was that if the front end blocked any invalid data from being submitted, a bad request would never reach the server, making backend validation redundant.
- I recognize that relying solely on client-side validation posed a severe threat to our database integrity. I explained to the team mate that all our backend endpoints were inherently exposed. Anyone with basic technical knowledge could use tools like Postman or curl to hit our API routes directly, bypassing the front end and therefore the validation rules.
- This was a huge risk because any corrupt data sent through these direct backend requests would be stored straight into the database without any validation.
- Instead I proposed to do validation both on the front end as well as the back end. Validation on the front end ensured a better user experience. For example if the user entered an incorrect date, they would be notified of it and they could change it to the correct one. At the same time we also needed to do back end validation just to guarantee data integrity.
- When I walked my team mate through the potential risks to our database, my team mate fully understood the exposure. We ultimately implemented a robust validation logic both on the front end and the back end. This choice kept our database perfectly clean while also ensuring a good user experience on the front end. Following best practices like this throughout our project led to us being the joint winners amongst 30 teams.

**Q7. Give me an example of a time when you used your fact-finding skills to solve a problem.**
- While working at Nokia, I was building and deploying my new micro service designed to communicate with several existing deployed services in our ecosystem. During the integration testing phase, my service's requests to the other micro services were completely failing. I needed to isolate the root cause of this failure but I had no idea whether the bug was from my local code, the external services, or the shared infrastructure.
- I began by reviewing my own service's logic. Once I verified that my code was correct and that there were no bugs, I shifted my focus to the other services and the shared infrastructure.
- After reading the error logs from my service's Kubernetes pod, I suspected that this bug was from the CI/CD pipeline. And I was correct. Because when I reviewed the code in the CICD configuration files, I found the bug that was causing this issue.
- The standard protocol was that whenever new code was pushed, the automated pipeline would build a new container image for that service and push it to two places in our image registry: a specific timestamp folder and a global latest folder. Images in the latest folder would be deleted after 7 days. However, someone had altered the pipeline configuration to only push images to the timestamp folder. I suspected that a developer would have hard-coded this during a temporary debugging session and might have forgotten to revert the pipeline script back to the regular standard. As a result, my service was unable to pull latest images of other services which was causing the issue.
- The solution was simple and I had to only change a couple of lines in the deployment script to revert back to the default protocol. I safely modified the configuration to ensure that images were correctly mirrored back to the latest repository folder, triggered a fresh build, and verified that my service now could seamlessly establish cross-service communication. My systematic fact-finding turned a highly frustrating architectural blocker into a clean infrastructure fix.
- Because my manager had been away from this specific application for a few weeks, he wasn't aware of this issue. I presented the issue, the root cause, and my verified fix. He was incredibly pleased with my proactivity and autonomy and immediately approved the changes into production. This investigation prevented further team-wide deployment friction and kept our micro service integration completely unshaded.

**Q9. Give me a specific example of a time where you used good judgment and logic in solving a problem.**
- During the planning phase of Fit4Me all the group members came together to brainstorm on the features that we wanted to include in the proposal document. Each member had a lot of ideas and there was a lot of excitement about a lot of features. Each member was also keen to lead the development of their favorite feature so that we could have as many features as possible in our app.
- However I recognized a major operational risk in this approach. If we overcommit to too many complex features, we risk spreading our resources across a lot of features, which could lead to conflicts and result in an app with a lot of half-baked features and poorly tested code.
- I had experienced a similar disaster in a much smaller project in the previous year so I could only imagine what would've happened in a large-scale project like this one.
- So I suggested a structured framework to scope the features that we wanted to include in the proposal document. The basic idea was to divide the features into two categories:
	1. The core features or the minimum viable product. These were the absolute non-negotiables required for the core functionality of the app. In our case this meant focusing on the ability for users to create exercises or workouts, to track exercises or workouts, and to finally go back and see their history. This also meant that we needed to define what a user is and allow users to log in and sign up to the application.
	2. Secondary Features: These were treated as add-ons that enhanced the user experience but were not necessary for the core app to function. For example features like the ability to follow another profile, the ability to message another user, etc.
- So we settled on a plan where all the group members would initially focus 100% on completing all the core features. This would ensure that all the members were working towards the same goal and that there were no conflicts. Because each member was also excited to implement their own feature, this would drive the group to complete the first part much earlier than the deadline that we had set.
- Once the core features were implemented and thoroughly tested, each member would pick up their favorite feature and work on it. This would minimize the possibility of conflicts because every developer would be familiar with the structure of the codebase and would have an idea of how things worked, which would make adding new features easier.
- Applying this logical framework proved to be a great call. We were able to implement all the code features and robustly test each one of them. Then we had ample time to implement our secondary features without any last-minute panic. The final application was impressive and because we had tested the core features thoroughly, we were able to demonstrate the app live during the final presentation.
- We were one of the few groups that were able to present the application live, ultimately winning joint first place amongst 30 other teams.
