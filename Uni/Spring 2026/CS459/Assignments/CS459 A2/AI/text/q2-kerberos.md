# Question 2: Kerberos

## 2(a) How do service servers verify the authenticity of the client using the ticket?

The service server verifies the client by checking both the service ticket and the authenticator.

First, the client presents a ticket that was created by the Ticket Granting Server (TGS) and encrypted with the long-term secret key shared between the TGS and that service server. Since only the TGS and the service server know that key, the client cannot forge or modify the ticket contents.

Second, the client sends an authenticator encrypted under the client-server session key contained inside the ticket. After decrypting the ticket, the service server obtains that session key and uses it to decrypt the authenticator. If decryption succeeds and the client identity inside the authenticator matches the identity inside the ticket, the server knows the sender possesses the correct session key and is therefore the legitimate client to whom the ticket was issued.

## 2(b) How does the authentication server protect a ticket-granting ticket from alteration?

The authentication server protects the ticket-granting ticket (TGT) by encrypting it with the secret key of the Ticket Granting Server.

Because the client does not know the TGS secret key, the client cannot alter the TGT and then re-encrypt it correctly. Any modification would be detected when the TGS later tries to decrypt and parse the ticket. In other words, the confidentiality and integrity of the TGT come from encryption under a key not known to the client or an adversary.

## 2(c) How are replay attacks prevented?

Kerberos prevents replay attacks mainly through authenticators, timestamps, short lifetimes, and replay checking.

- Each time the client uses a ticket, it also sends a fresh authenticator.
- The authenticator contains the client identity and a current timestamp.
- The authenticator is encrypted with the relevant session key, so an attacker cannot create a fresh one.
- The server checks that the timestamp is within an allowed time window.
- The server can also remember recently seen authenticators and reject duplicates.

As a result, even if Mallory records an earlier ticket and authenticator, replaying them later will fail because the timestamp will be stale or the authenticator will already have been used.

## 2(d) List the five keys used in Kerberos and the purpose of each

There are a few equivalent ways to name the keys in Kerberos. A standard set of five is:

1. **Client long-term key (`Kc`)**  
   This key is derived from the client’s password. The Authentication Server (AS) uses it to encrypt the part of the AS reply intended for the client, including the client-TGS session key.

2. **Ticket Granting Server long-term key (`Ktgs`)**  
   This key is shared by the AS and the TGS. It is used to encrypt the ticket-granting ticket, so only the TGS can read it.

3. **Client-TGS session key (`Kc,tgs`)**  
   This temporary session key is generated by the AS. It is sent to the client encrypted under `Kc`, and also placed inside the TGT encrypted under `Ktgs`. The client then uses `Kc,tgs` to encrypt the authenticator sent to the TGS.

4. **Application server long-term key (`Kv`)**  
   This key is shared between the TGS and the target service server `V`. The TGS uses it to encrypt the service ticket, so only that server can read it.

5. **Client-server session key (`Kc,v`)**  
   This temporary session key is generated by the TGS. It is sent to the client encrypted under `Kc,tgs`, and also included in the service ticket encrypted under `Kv`. The client and service server then use it to protect authenticators and optionally secure later communication.

## 2(e) How is the session key distributed by the authentication server?

The Authentication Server generates the client-TGS session key and distributes it in two places at the same time:

- It sends the session key to the client in the AS reply, encrypted with the client’s long-term key `Kc`.
- It also embeds the same session key inside the ticket-granting ticket, encrypted with the TGS long-term key `Ktgs`.

This way, the client learns the session key, and the TGS later learns the same session key when it decrypts the TGT. Since both parties receive the same key securely, they can use it for the next stage of the Kerberos protocol.
