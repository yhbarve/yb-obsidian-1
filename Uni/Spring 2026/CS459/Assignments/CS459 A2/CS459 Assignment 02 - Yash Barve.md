### Question 02
**(a)**
- The application server verifies the client by decrypting the service ticket using its own secret share key to extract the session key.
- It then uses the session key to decrypt the client's authenticator, which contains a timestamp and the client ID.
- If the client ID matches and the timestamp is fresh, authenticity is proven.
- - -
**(b)**
- The authentication server encrypts TGT using the secret key $K_{TGS}$ of the ticket granting server.
- The client or any outside adversary does not have access to $K_{TGS}$.
- Therefore, any alteration to the TGT will corrupt the data, causing decryption to fail at the TGS stage.
- - -
**(c)**
- The Kerberos protocol uses an authenticator containing the current timestamp.
- The server checks this timestamp against its local clock, and if the message window is outside an acceptable range, the packet is dropped
- Additionally, servers maintain a replay cache within that time range to catch duplicate messages.
- - -
**(d)**
1. Client Secret Key: Known only to the client and the authentication server (AS). It is used to decrypt the initial response packet from A, which contains the ticket granting server (TGS) session key and the TGT.
2. TGS Secret Key: Known only to the AS and the TGS. It is used by the AS to encrypt the TGT and by the TGS to decrypt it.
3. Application Server Secret Key: Known only to the TGS and the specific application server. It is used by the TGS to encrypt the final service ticket (ST).
4. TGS Session Key: A temporary session key generated by the KDC for secure communication between the client and the TGS. It encrypts the TGS request details and the authenticator.
5. Service Session Key: A temporary session key generated by the TGS for secure application traffic between the client and the application server.
- - -
**(e)**
- The authentication server distributes the session key as two copies:
	1. The first copy is intended for the TGS. It is wrapped inside the TGT and encrypted under the TGS secret key.
	2. The second copy is intended for the client. It is placed outside the TGT but encrypted under the client's secret key. The client can decrypt it and read the session key.

### Question 03
**(a)**
- YES.
- SSL/TLS prevents replay attacks using the random nonce values generated by the client and server during the handshake phase.
- The client and server also have a shared key that is established during the asymmetric key exchange phase.
- These three keys are used to derive the final session keys.
- If an adversary intercepts a handshake session and replays the messages later, the new session will use a fresh server Mons.
- This would cause the final session key to mismatch, forcing the target to terminate the connection.
- - -
**(b)**
- YES.
- Man-in-the-middle attacks are blocked during the SSL/TLS handshake via asymmetric authentication using PKI and CAs.
- The server transmits its digital server certificate and signature directly to the browser. The client passes the certificate chain and verifies that the host name matches the requested URL.
- The server must also sign all handshake messages using its private key corresponding to the verification key in the certificate.
- An adversary cannot replicate the signature without having the server's private key. This prevents any man-in-the-middle attacks.
- - - 
**(c)**
- YES.
- Once the handshake is successfully completed, all the data sent over the connection is protected.
- SSL/TLS record protocol takes raw application layer data and encrypts it using strong symmetric ciphers. It also adds a MAC for integrity.
- Therefore, any data traveling across the connection is encrypted. So any adversary sniffing the network will not have access to the original data.
- - -
**(d)**
- YES, but not directly.
- SSL/TLS prevents IP spoofing indirectly using the MACs and sequence numbers that every data packet includes.
- An attacker does not know the secret session keys and therefore cannot generate a valid payload MAC or the exact or correct sequence numbers.
- Therefore, the receiving hosts will fail to verify the block and discard the bogus data.
- - -
**(e)**
- NO.
- SSL/TLS cannot mitigate a SYN flood attack.
- This is because SSL/TLS operates strictly at the transport layer above the raw TCP execution.
- In SYN flooding, the attacker sends a lot of TCP SYN packets but never completes the handshake. Because the TCP handshake is never finished, the connection is never fully established.
- TLS relies on a TCP connection to send its own handshake messages. Therefore, in this case, TLS is unable to prevent SYN flooding.
